# Related work and technical comparison

Reference metadata and linked primary sources were checked on 17 October 2026. This is a comparison of mechanisms and trust assumptions, not a performance ranking of products. RBAC, ABAC, OAuth, Macaroons, SPIFFE, A2A and Certificate Transparency were **not** implemented as competing end-to-end systems in these experiments. Numerical findings belong to the three experiment reports and their raw CSVs.

## Authorization, identity and delegation

| Approach | Authority provenance and trust assumption | Delegation and revocation | Relationship to ChainGuard-AI |
| --- | --- | --- | --- |
| RBAC [1] | A trusted administrator assigns permissions through roles. Roles make organizational policy manageable; a role name itself does not authenticate a caller. | Hierarchies and constraints can express policy; downstream grant revocation depends on the chosen implementation. | ChainGuard retains readable agent roles but evaluates explicit scoped grants and ancestry. This is not a formal implementation or experimental replacement of the complete NIST RBAC model. |
| ABAC [2] | A trusted policy decision point evaluates subject, object, operation and environmental attributes. Attribute authenticity remains necessary. | Rules may include time and relationships; ABAC alone does not prescribe this project's signed grant ledger or cascading algorithm. | Time windows and permission scope resemble attribute conditions. ChainGuard does not supply a general ABAC policy language or policy administration framework. |
| OAuth 2.0 [3], with token exchange [4] | The resource server trusts an authorization server and validates the relevant access token. Token exchange can distinguish an actor from the subject represented. | Token lifetime, status policy and implementation determine revocation propagation. Token exchange supports delegation/impersonation semantics but is not evidence that every deployment has automatic cascading revocation. | ChainGuard uses registry-bound Ethereum request signatures, not OAuth access tokens, an OAuth authorization server or RFC 8693 token exchange. OAuth is a possible integration layer, not a measured weaker baseline. |
| DPoP [5] and current OAuth security guidance [6] | A request proof binds a key to sender-constrained OAuth tokens and request information. Correct token validation and transport security remain necessary. | Unique proof identifiers, time checks and server policy address replay; proof of key possession alone does not grant permission. | ChainGuard similarly binds an actor, operation, payload digest, domain, nonce and time window, but its custom EIP-191 envelope is **not DPoP compliant** and is not a JWT. |
| Macaroons [7] | Cryptographic credentials support attenuating authority using contextual caveats, with verification rooted in issuer trust and key material. | Holders can restrict credentials and delegate; caveats and discharge credentials support contextual checks. Application policy still governs invalidation. | This is a genuine cryptographic delegation approach, not a name-based permission model. ChainGuard instead uses publicly recoverable signatures and explicit parent-grant references; no Macaroon compatibility is implemented or benchmarked. |
| W3C Verifiable Credentials 2.0 [8] | Issuers make cryptographically protected claims; holders present them; verifiers apply their own trust and business policies. Authenticity does not establish that a claim is true. | Validity and status are represented by the model and associated mechanisms; application-specific authority still needs validation. | ChainGuard's custom scoped credential dictionaries are **not claimed to conform** to the W3C data model or a W3C proof suite. No DID method, selective disclosure or zero-knowledge presentation is implemented. |
| SPIFFE / Workload API [9] | A workload identity infrastructure issues short-lived cryptographic identity documents and trust bundles, based on workload attestation and a trust domain. | Identity issuance and renewal are separate from an application's resource permission and delegation policy. | Relevant to authenticating deployed agent workloads. ChainGuard currently resolves agent names to registered Ethereum addresses; it does not implement SPIFFE, SPIRE, SVIDs or workload attestation. |
| A2A protocol v1.0 [10] | Agent interfaces advertise supported authentication/security schemes; endpoint security relies on the selected mechanisms, including OAuth, OIDC or mutual TLS. | Interoperable agent tasks and security requirements are distinct from the particular grant-ancestry and revocation policy enforced by an application. | ChainGuard is a controlled multi-agent governance prototype, not an A2A protocol implementation. A2A is a possible interoperable transport integration; the comparison does not assert that A2A agents lack security controls. |

## Audit logging and externally checkable evidence

| Approach | What detects an altered history? | Important trust and availability limits | Cost/scalability considerations |
| --- | --- | --- | --- |
| Conventional append-only local log | Protected append-only storage, access controls, retained backups or an independent copy can reveal unauthorized changes. Ordinary writable JSONL alone is not a cryptographic proof. | The auditor depends on the administrator/storage controls. An attacker allowed to replace all files can replace an unprotected history. | No blockchain transaction is required. Storage administration and trusted retention still have costs; this work does not benchmark a production WORM appliance or database. |
| Cryptographic hash-chain log | Each digest commits to the previous digest and current record. A retained trusted head and length expose changes, deletion, insertion or reordering, even if an attacker recomputes every local link. | If the attacker can also replace the only verification head/checkpoint, a recomputed chain can be internally consistent. A separately protected or witnessed checkpoint changes this assumption. | Hashing and checkpoint management add overhead. The experiment's deliberately simple full JSON snapshot baseline is not an optimized database or append-only binary implementation. |
| Publicly monitored Merkle log, such as CT [11] | Inclusion proofs and consistency checks against retained signed tree heads support transparent auditing without a blockchain. | Auditors must obtain, retain and compare appropriate log views; the log and monitoring ecosystem still need availability and accountability mechanisms. | Compact proofs and external monitors are another design choice. This work does not benchmark CT or implement its complete protocol. |
| ChainGuard Merkle roots anchored in an EVM registry | The auditor recomputes canonical record hashes and ordered batch roots and checks the authenticated registry's commitments, receipt/event evidence and batch inventory. | An off-chain storage attacker cannot change an already accepted chain commitment under the experiment's trusted-chain/RPC assumption. Anchoring does not prove the semantic truth of an event, recover missing records or prevent a compromised authorized root from committing bad new data. | One root transaction covers a batch, while trust-event transactions are separate. Gas, receipt waits, RPC availability, chain finality and operational complexity are additional costs. Local Hardhat timings do not measure public-network confirmation latency. |

The hash-chain baseline and blockchain variant use the same production record canonicalization and authorization engine. Their security difference is the location and independence of the verifier's checkpoint. A correctly protected hash-chain checkpoint can provide the same tested detection property against storage rewriting. Blockchain adds a separately addressable commitment that an auditor can query without accepting the current local log head; it is not the only way to provide an external witness.

## What the implementation adds, and what remains a research claim

The implementation combines (a) cryptographically authenticated requests, (b) scoped grant ancestry and downstream invalidation, (c) an existing Isolation Forest behavioral signal, and (d) externally anchored ordinary-action audit batches. The contribution evaluated here is their concrete integration and the reproduced/fixed implementation weaknesses. No new signature primitive, consensus protocol, Isolation Forest algorithm or universal access-control model is claimed.

The corrected Python engine authenticates caller signatures against trusted registered public addresses, validates signature-bound grant metadata and exact parent grants, and preserves independently valid paths. The optional `GrantAuthority.sol` extension makes grant ancestry and transitive validity queryable on an isolated local EVM deployment. Existing Sepolia evidence uses the original `AgentTrustRegistry`; the extension has **not** been deployed or retroactively added to that public evidence. Local enforcement and on-chain evidence must be reported separately.

| Main statement | Implementation evidence | Appropriate experimental evidence |
| --- | --- | --- |
| A client-supplied root name is insufficient to issue a root grant. | `backend/core/authorization/authentication.py`: `RequestVerifier.authenticate`, `registered_verifier`; `agents.py`: `grant_root_permission` | Experiment 3 before/after root spoofing and permanent signed-request/API tests |
| A revoked parent does not authorize its descendants through the revoked grant. | `agents.py`: `authority_paths`, `delegate_permission`, `decommission_agent`; `blockchain/contracts/GrantAuthority.sol`: `wasValidAt` | Experiment 2 preserved-baseline comparison, independent-path cases and local contract integration tests |
| An externally retained checkpoint changes resistance to whole-history rewriting. | `backend/research/audit_baseline.py`: `verify`; `experiment1.py`: `verify_chain_inventory`, tampering cases | Experiment 1's two checkpoint policies; these are controlled attacker models, not field attack frequencies |
| Public batch proof verification still concerns existing historical evidence. | `backend/core/blockchain/batch_verifier.py`; saved public root and original audit records | Separate read-only Sepolia verification, not new local performance CSVs |
